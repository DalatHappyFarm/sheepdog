How sheepdog works

{{DIAGRAM}}

Hooks and the orchestrator write into one small server; the page and Claude read from it. The tables below are generated from the code, so they cannot go stale.

How a decision travels

  1. The orchestrator posts a review card: sheepdog brief KEY --file review.md --option ... (waiting becomes you).
  2. You open it on the board. The page already has it, from its 3 s poll of /api/state.
  3. You click an option or reply: the server writes a pending row in decisions and a timeline note, and hands the task back to the agent. A task with no review card takes a reply only; it is delivered to the task's worktree folder.
  4. Exactly one of sheepdog wait or the next UserPromptSubmit hook in that folder claims it (status delivered) and Claude sees the text.
  5. Claude acts and runs sheepdog done ID; the page shows Done.

Parents and sub-tasks

A big task is a parent and its pieces are sub-tasks: sheepdog task T32 --parent T31 sets tasks.parent (one level only; the parent must exist; --parent "" clears it). A parent has no status of its own: it is derived from its sub-tasks (all done = done, any blocked = blocked, any review or testing = review, any building or analysing = building, else planned) and needs you when a sub-task does, but only the sub-tasks appear in Needs you.

Moving parts

  • bin/sheepdog: the server, the CLI and the hook client, one static binary built from cmd/sheepdog with internal/store, internal/server and internal/cli (Go; one dependency, modernc.org/sqlite, no CGO; the web/ pages and the brand/ PNGs are embedded)
  • web/: the pages, shared by both implementations; sheepdog.py and test_sheepdog.py: the Python original, kept as the rollback and as the contract's reference
  • tests: go test ./..., python3 -m unittest, contract/run.py (a 224-step contract, golden from Python, run against either server) and contract/bench.py
  • hooks: accepted only from the folders in SHEEPDOG_ALLOW (or serve --allow DIR) and below when it is set, every folder when it is not; sheepdog purge --outside-allow removes what other folders left
  • privacy: paths and names are rewritten before anything is stored (a folder under an allowed root becomes name:path, the home directory ~, temp dirs <tmp>, the user and host name <user> and <host>); sheepdog scrub rewrites rows stored earlier
  • .token: the access token (SHEEPDOG_TOKEN); ~/.local/share/sheepdog/board.db: the SQLite data
  • ~/.claude/settings.json: the hook entries (curl to /api/hook)
  • your orchestrator's wrapper script (optional): it calls the CLI (bin/sheepdog, or python3 sheepdog.py)
